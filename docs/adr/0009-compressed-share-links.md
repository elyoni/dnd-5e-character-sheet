# Compress share-link payloads instead of hosting them

A filled-out character's `#char=...` share link can run to ~17,000 characters (measured against a realistic stress-test character), long enough that some messaging apps split it across multiple messages when pasted. We chose to gzip the JSON payload (via the native `CompressionStream` API, no vendored library) before base64-encoding it, rather than moving to a hosted-storage-plus-short-ID scheme — measured gzip alone at ~7.7x reduction on that same stress-test character, which was judged good enough to avoid adding a backend/storage dependency to an app whose whole architecture (single self-contained HTML file, zero runtime network dependency) is built around not having one.

We use the native `CompressionStream` API rather than vendoring a JS gzip library (the pattern used for Three.js/cannon-es): it's supported on all mainstream browsers since 2023 (Chrome/Edge 80+, Firefox 113+, Safari 16.4+), and we judged that floor acceptable for this app rather than worth another vendored dependency. A browser without it (encode side) silently falls back to producing the old uncompressed link.

Old and new payloads are told apart by an in-payload marker, not a new hash key: `decodeBase64ToState` tries gzip-decompress first and falls back to plain-JSON parse on failure, so `#char=`/`#charbundle=` keep meaning the same thing forever and links already shared before this change keep working unchanged. This mirrors how `hydrate()` already absorbs old JSON shapes silently at load time rather than versioning the schema in the field names.
